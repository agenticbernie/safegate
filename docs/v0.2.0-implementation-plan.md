# SafeGate v0.2.0 Technical Implementation Audit and Plan

**Goal:** Give migration authors evidence-backed PostgreSQL 16 lock and rewrite findings while preserving offline static analysis and the v0.1.0 report contract.

**Architecture:** Parse SQL locally, derive conservative statement-level facts, and retain uncertainty when syntax cannot establish catalog or runtime state. Optional user-supplied context may annotate consequences, never contradict facts or weaken a decision. PostgreSQL is used only by a disposable, isolated test fixture, never by SafeGate itself.

**Stack:** Python 3.12, pglast 6.17, Pydantic 2, pytest, PostgreSQL 16. **Spec:** task requirements supplied with this audit. Audit date: 2026-11-03.

**Constraints:** No database connections from the product; no `SAFEGATE_DATABASE_URL`, telemetry, runtime monitoring or remote SQL/schema upload. No production code, commit, or push in this audit. PG16 container tests use no network. All behavioral claims below are scoped to successful operations and PG16 unless stated otherwise.

## 1. Current architecture: verified observations

- The project is v0.1.0 and pins pglast 6.17 ([pyproject.toml:3](../pyproject.toml#L3), [pyproject.toml:11](../pyproject.toml#L11)). Parsing is local; [postgres.py:82](../src/safegate/parser/postgres.py#L82) returns raw parse nodes and tracks transactional context. [scan.py:47](../src/safegate/scan.py#L47) runs the rules and [scan.py:26](../src/safegate/scan.py#L26) maps decisions to status. A parse error becomes `UNKNOWN`.
- **Model compatibility:** `Finding` is a frozen slotted dataclass ([base.py:21](../src/safegate/rules/base.py#L21)). A trailing field with a default can be added internally without changing existing constructor calls, including the parser's ([postgres.py:52](../src/safegate/parser/postgres.py#L52)). This does **not** automatically change JSON: `_report_finding` explicitly maps fields ([report.py:53](../src/safegate/report.py#L53)). Adding JSON keys directly is incompatible with the existing strict `FindingReport` and `ScanReport` (`extra="forbid"`) and `schema_version: Literal["1.0"]` ([report.py:22](../src/safegate/report.py#L22), [report.py:44](../src/safegate/report.py#L44)). See the opt-in solution below; arbitrary external consumers cannot be guaranteed compatible with a new shape.
- **AST capability, verified locally:** Loading the cached, pinned pglast 6.17 without a server shows `Constraint.raw_expr` is a `FuncCall` for `DEFAULT clock_timestamp()`; `AT_AlterColumnType` exposes the target `ColumnDef.typeName`, `typmods`, and the `USING` expression as `ColumnDef.raw_default`; `UNIQUE USING INDEX ix` is `AT_AddConstraint`, `CONSTR_UNIQUE`, `Constraint.indexname='ix'`. `MergeStmt.mergeWhenClauses` and `InsertStmt.onConflictClause` are also exposed. PostgreSQL's [raw parse-node definitions](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/include/nodes/parsenodes.h) support this interpretation. The AST supplies syntax, **not** overload resolution, `pg_proc.provolatile`, cast functions, preexisting type/typmod, constraints, index validity, search path or actual data. It is insufficient to prove arbitrary expression volatility or binary coercibility on its own.
- **SG-004:** [alter.py:31](../src/safegate/rules/alter.py#L31) recognizes only an explicit default constraint; [alter.py:44](../src/safegate/rules/alter.py#L44) explicitly leaves fast-path analysis unverified, and all such statements receive medium/REVIEW. It does not classify nested expressions or implicit type/domain defaults, generated/identity cases, relation kind, simultaneous subcommands or associated validation scans. A nonvolatile default is not evidence that the ACCESS EXCLUSIVE lock disappears.
- **SG-006:** [alter.py:116](../src/safegate/rules/alter.py#L116) recognizes the operation only; [alter.py:122](../src/safegate/rules/alter.py#L122) leaves all conversions unverified. Neither old type/typmod nor `USING`, domain, collation, indexes, partitioning or other subcommands are analyzed. Target-only SQL normally cannot establish a conversion pair.
- **SG-003:** [constraints.py:7](../src/safegate/rules/constraints.py#L7) selects `AT_AddConstraint` and [constraints.py:27](../src/safegate/rules/constraints.py#L27) treats all PRIMARY/UNIQUE forms alike; [constraints.py:40](../src/safegate/rules/constraints.py#L40) falsely says attachment creates an index and recommends creating one again. An existing index is syntactically visible, but its eligibility and column nullability are unknown; attachment still requires ACCESS EXCLUSIVE, and may scan for NOT NULL. Preserve its existing BLOCK policy while correcting the explanation.
- **SG-009:** [destructive.py:238](../src/safegate/rules/destructive.py#L238) handles UPDATE/DELETE without WHERE or with simple folded literals; unknown predicates are REVIEW and proven false yields no finding. [destructive.py:256](../src/safegate/rules/destructive.py#L256) ignores MERGE and INSERT ON CONFLICT entirely, which can currently result in SAFE despite unassessed modification scope. Joined UPDATE/DELETE scope and arbitrary expressions remain unknown. Existing literal folding is deliberately limited ([destructive.py:32](../src/safegate/rules/destructive.py#L32)); it is not proof of general SQL expression semantics.
- **Other relevant gaps:** SG-002 only mentions writes ([index.py:83](../src/safegate/rules/index.py#L83)); ordinary DROP also blocks plain reads. SG-010 handles CREATE but not DROP INDEX CONCURRENTLY in a transaction ([index.py:91](../src/safegate/rules/index.py#L91)). Configuration rejects unknown root keys ([config.py:22](../src/safegate/config.py#L22), [config.py:76](../src/safegate/config.py#L76)). Existing explicit rule disablement and allowlists can suppress findings ([base.py:44](../src/safegate/rules/base.py#L44), [base.py:88](../src/safegate/rules/base.py#L88)); severity overrides currently change severity but not decision. Hints must not be implemented as any of these overrides.
- The scanner itself has no network path, but the **optional existing GitHub Action** publishes finding metadata to GitHub ([README.md:15](../README.md#L15), [action.py:132](../src/safegate/github/action.py#L132)). Do not characterize the whole product as having no network calls. Default v1 output and GitHub reporting must not add hints, SQL, or schema data. [README.md:114](../README.md#L114) and the older PRD describe runtime metadata; they conflict with this task and must be corrected or explicitly marked superseded during implementation.

## 2. PostgreSQL 16 behavior verification matrix

**Definitions.** Required mode means the relevant table-level lock acquired for the described successful operation; related tables, indexes, partitions, triggers and explicit `LOCK` can add locks. Potential blocking compares that mode to ordinary `SELECT` (`ACCESS SHARE`) and INSERT/UPDATE/DELETE (`ROW EXCLUSIVE`) on the same relation in another transaction. It is not an observation that anybody is waiting. Lock acquisition and transaction duration, existing transactions and lock queues determine actual contention, which is **UNKNOWN to static analysis**. Even a concurrent command can wait and lock queues can have indirect effects. Row locks, uniqueness checks, foreign keys, triggers and application-level blocking are separate. See [PG16 explicit locking and conflict table](https://www.postgresql.org/docs/16/explicit-locking.html).

| Statement / successful case | Required table lock | Potential conflict with plain reads / ordinary writes | Heap rewrite / qualifications |
| --- | --- | --- | --- |
| `CREATE INDEX` | SHARE | Reads: no; writes: yes. | No heap rewrite; index is built. [CREATE INDEX](https://www.postgresql.org/docs/16/sql-createindex.html), [locks](https://www.postgresql.org/docs/16/explicit-locking.html). |
| `CREATE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE | Reads: no; ordinary writes: no; conflicts with other maintenance/schema locks. | No heap rewrite. Multiple phases wait for transactions; cannot run in a transaction block. A concurrent build directly on a partitioned parent is unsupported; build child indexes then attach/create parent as documented. Temporary tables are built nonconcurrently. [CREATE INDEX](https://www.postgresql.org/docs/16/sql-createindex.html). |
| `DROP INDEX` | ACCESS EXCLUSIVE on indexed table | Reads: yes; writes: yes. | No heap rewrite; removes index. [DROP INDEX](https://www.postgresql.org/docs/16/sql-dropindex.html). Index-to-table mapping is unknown from DROP syntax alone. |
| `DROP INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE on table, plus phase-specific index locks | Reads: no direct table-lock conflict; ordinary writes: no direct table-lock conflict. | No heap rewrite. PG waits for old transactions and later obtains ACCESS EXCLUSIVE on the **index**; do not say the procedure never waits or has no indirect effect. One index only, no CASCADE, no constraint-backed or partitioned index, and no transaction block. [DROP INDEX](https://www.postgresql.org/docs/16/sql-dropindex.html), [PG16 index.c](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/catalog/index.c#L2039-L2052), [wait phases](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/catalog/index.c#L2142-L2184). |
| `ALTER TABLE ADD COLUMN` | ACCESS EXCLUSIVE | Reads: yes; writes: yes. | Ordinary stored heap, no default or nonvolatile resolved default: normally no heap rewrite; volatile resolved default: rewrite. Generated columns, constrained domains, relation kind, implicit casts/defaults and other subcommands can change this; unknown unless proved. Constraint validation can scan without rewriting. [ALTER TABLE notes](https://www.postgresql.org/docs/16/sql-altertable.html), [PG16 fast-path conditions](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/commands/tablecmds.c#L6731-L6831). |
| `ALTER TABLE ALTER COLUMN TYPE` | ACCESS EXCLUSIVE | Reads: yes; writes: yes. | Normally rewrite; exceptions include identity-preserving binary coercion and certain unconstrained domains; source also has a session-time-zone-dependent timestamp exception. Unresolved old type, casts, `USING`, domains, or timezone: UNKNOWN. Indexes may independently rebuild. [ALTER TABLE](https://www.postgresql.org/docs/16/sql-altertable.html), [PG16 rewrite decision](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/commands/tablecmds.c#L11953-L12004). |
| `ADD PRIMARY KEY`, `UNIQUE`, `CHECK`, `EXCLUDE`; `ADD ... USING INDEX` | ACCESS EXCLUSIVE | Reads: yes; writes: yes. | Constraint/index building and validation can scan/build indexes, not in itself a heap rewrite. `USING INDEX` attaches an eligible existing index; PRIMARY KEY may scan for NOT NULL. It is unsupported on partitioned tables. [ALTER TABLE](https://www.postgresql.org/docs/16/sql-altertable.html). |
| `ADD FOREIGN KEY` | SHARE ROW EXCLUSIVE on both referencing and referenced tables | Reads: no; writes: yes on both. | Validation may scan; `NOT VALID` avoids the initial validation scan where supported, not the lock. No inherent heap rewrite. Combined subcommands take the strictest mode. [ALTER TABLE](https://www.postgresql.org/docs/16/sql-altertable.html). |
| `UPDATE` / `DELETE` | ROW EXCLUSIVE on target; ACCESS SHARE on additional referenced tables | On target, no table-level conflict with plain reads or ordinary writes; row-level conflicts are possible. | Row modifications create new/dead tuple versions, not an ALTER-style whole-heap rewrite. Actual rows and row-lock contention unknown. [locks](https://www.postgresql.org/docs/16/explicit-locking.html), [UPDATE](https://www.postgresql.org/docs/16/sql-update.html), [DELETE](https://www.postgresql.org/docs/16/sql-delete.html). |
| `MERGE` | ROW EXCLUSIVE on target; ACCESS SHARE on additional referenced tables | Same target table-lock conflict as DML; row conflicts possible. | No inherent whole-heap rewrite. Branch conditions and join do not prove number of target rows. [MERGE](https://www.postgresql.org/docs/16/sql-merge.html), [locks](https://www.postgresql.org/docs/16/explicit-locking.html). |
| `INSERT ... ON CONFLICT DO UPDATE` / `DO NOTHING` | ROW EXCLUSIVE on target; ACCESS SHARE on additional referenced tables | Same target table-lock conflict as DML; unique-index and row interactions may wait. | No inherent whole-heap rewrite. Conflict-target and conditional action are not proof of cardinality. [INSERT](https://www.postgresql.org/docs/16/sql-insert.html), [locks](https://www.postgresql.org/docs/16/explicit-locking.html). |

### Type conversion matrix

These are **conditional source-verified expectations**, not results of a live test in this audit. Apply only when the old type and typmod are independently known, the expression is a proved identity, the relation has storage, and no other command forces a rewrite. Unknown type history means `rewrite=unknown`, never an assumed match. PostgreSQL's [varchar support function](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/utils/adt/varchar.c#L525-L557), [ALTER TABLE notes](https://www.postgresql.org/docs/16/sql-altertable.html), and [pg_cast catalog](https://www.postgresql.org/docs/16/catalog-pg-cast.html) provide the basis.

| Old → new | Binary / typmod fact | Heap rewrite expectation |
| --- | --- | --- |
| `varchar(n)` → `varchar(m)`, `m >= n` | Same underlying type; widening typmod coercion simplifies to a relabel. | No, subject to conditions above. |
| `varchar(n)` → unbounded `varchar` | Typmod restriction removed. | No, subject to conditions above. |
| `varchar(n)` → `varchar(m)`, `m < n`; unbounded → `varchar(m)` | Same type is not enough: narrowing requires a length coercion/check. | Yes if operation succeeds; explicit `USING` casts may truncate, while implicit conversion can fail for overlength values. |
| `integer` → `bigint` | Built-in numeric conversion is not binary coercible. | Yes if successful; confirm against the pinned PG16 cast catalog and fixture. |
| `text` ↔ unbounded `varchar` | Binary-compatible; no typmod narrowing. | No under conditions above; index equivalence still separately evaluated. |
| `text` / unbounded `varchar` → bounded `varchar(m)` | Length check is required even where base representations are binary compatible. | Yes if successful. |
| Domain, custom type/cast, timestamp ↔ timestamptz, nonidentity `USING`, unknown source | Depends on catalog, resolved expression, constraints or timezone. | UNKNOWN statically by default; do not infer from spelling alone. |

The docs and source describe domain exceptions in different directions; use the [actual PG16 implementation](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/commands/tablecmds.c#L11953-L12004), catalog resolution, and tests before expanding the registry. A transformed `USING` expression can force a rewrite even for a normally compatible pair. A rewrite of one partition is not a rewrite of a storage-less parent. A changed index filenode is not a heap rewrite.

### Default volatility classifier

**Proposal:** version-keyed, checked-in, allowlisted PG16 registry keyed by resolved built-in schema/name/signature and expression shape, with source links and fixtures, not a name-only general catalog. Initial examples are `pg_catalog.now()` = STABLE and `pg_catalog.clock_timestamp()` = VOLATILE ([PG16 pg_proc.dat](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/include/catalog/pg_proc.dat#L2548-L2560)); both are non-immutable, but STABLE is nonvolatile. Use [function volatility definitions](https://www.postgresql.org/docs/16/xfunc-volatility.html).

Classify literal expressions only when their implicit type/input/coercion is proven built-in; recognize exact known SQL syntax such as `CURRENT_TIMESTAMP` only with documented resolution. Walk all child expressions: a resolved volatile call is evidence of possible volatility; assert volatility only when the call survives PostgreSQL's expression simplification, as with the direct qualified call in the fixture. In a conditional or otherwise simplifiable expression, use UNKNOWN unless survival is proved. Nonvolatile requires every function, operator, cast, argument, implicit conversion, domain check and default to be resolved and nonvolatile; otherwise UNKNOWN. Do not trust unqualified names that can resolve differently through `search_path`, overloads or user-defined objects. Unknown/custom functions, types, operators, domains and casts are UNKNOWN, even if their names resemble built-ins. No live `pg_proc` lookups, no expressions executed by the analyzer. Restrict initial positive claims to exact PG16 cases and retain REVIEW when fast-path preconditions are not established. `GENERATED`, identity, constrained domains, inherited/partitioned or foreign relations and mixed ALTER subcommands require independent checks. An unqualified `clock_timestamp()` can be tested in the PG16 fixture under a controlled search path, but should not be declared resolved from text alone.

## 3. Context hints and unknown semantics

**Proposal, contingent on product gate in §6:**

```toml
[tables."public.users"]
size = "large"
```

Sizes are user assertions about **row count**, not bytes: `small` <10,000; `medium` 10,000 through 1,000,000 inclusive; `large` >1,000,000; `unknown` or absent = UNKNOWN. These boundaries resolve the gaps in the requested example. Tables with wide rows or indexes can be expensive despite a small row count. Do not estimate time, I/O or certainty from a bucket.

Match only an explicitly schema-qualified AST identifier to a quoted dotted TOML key, preserving PostgreSQL identifier case/quoting; unqualified, ambiguous, renamed, dropped or partitioned relation identity is UNKNOWN. Do not use `search_path` assumptions. Reject malformed TOML, invalid values, unknown keys and duplicate/ambiguous mappings with `ConfigError`; never silently fall back to SAFE. Configuration is local, deterministic, opt-in and may be stale or wrong; record exactly which assertion was used, without timestamps or invented provenance.

Compute static finding/lock first. A hint may refine a separate advisory `estimated_rewrite_impact` and recommendation **only when a rewrite is verified or explicitly possible**, labeling it user-supplied; unknown rewrite stays unknown. It cannot change required lock, potential conflicts, evidence confidence, static decision, exit code, suppress a finding, turn BLOCK into SAFE, or downgrade severity. If severity adjustment is implemented, it may only increase a separate presentation severity, never override a higher explicit/static severity; prefer no severity adjustment until there is evidence it helps. Existing explicit disable/allowlist/override behavior remains as before, documented as policy, not as a hint; do not exploit it to silently defeat this rule.

Missing context is UNKNOWN in the context dimension; it does not imply the entire report must be UNKNOWN for SQL unrelated to context. For a relevant operation whose safety/rewrite cannot be established, retain at least REVIEW (or existing UNKNOWN on parser failure); never treat the missing information as affirmative safety. Current no-findings → SAFE behavior remains for operations whose covered analysis is complete; unsupported risky forms must receive an explicit REVIEW instead of silently passing. Keep `UNKNOWN` aggregation semantics and exits unchanged ([report.py:70](../src/safegate/report.py#L70), [README.md:31](../README.md#L31)).

**Migration history:** may only infer schema evolution from an explicitly supplied, complete, correctly ordered, successfully applied history with unambiguous names and supported DDL; all those assumptions require proof or explicit provenance. It can never infer cardinality/size, deployment success, drift, actual catalog or runtime state. No such completeness evidence exists in this repo. Recommend defer; if history is incomplete, dynamic, contradictory or branches, old type remains UNKNOWN.

## 4. Report schema and compatibility

**Proposal:** Keep the default JSON and GitHub Action output exactly schema `1.0`, with the same keys, field types, aggregation, `confidence`, and exit semantics. Add an opt-in CLI format selector such as `--report-schema 2.0`; `schema_version="2.0"` is a separate contract, not falsely advertised as parseable by strict v1 consumers. Do not silently route v2 output into the v1 Action parser or comment. Existing consumer code parsing default v0.2 output with the actual v0.1.0 models must pass. A consumer explicitly requesting v2 must upgrade. Preserve deterministic ordering. Changes in factual findings or decision for previously unassessed SQL are disclosed in release notes, not described as unchanged behavior.

Add a trailing defaulted `lock_impact: LockImpact | None = None` to the internal `Finding`; carry other fields with defaults or a separate immutable evidence object. In opt-in 2.0, each finding adds:

```json
{
  "lock_impact": [{
    "relation": "public.users",
    "required_mode": "ACCESS EXCLUSIVE",
    "plain_read_conflict": true,
    "ordinary_write_conflict": true,
    "runtime_contention": "unknown",
    "rewrite": "unknown"
  }],
  "context_hints_used": [],
  "evidence_confidence": {"lock": "verified", "rewrite": "unknown"}
}
```

This excerpt supplements, rather than replaces, every v1 finding field. `lock_impact` is a nullable array of impact objects, one per known relation or unresolved target; unknown mode/relation/conflict is null, never false. `rewrite` is `required`, `not_required`, or `unknown` under explicit successful-operation assumptions; a separate index/validation scan is not a heap rewrite. `evidence_confidence` is a typed object per claim with values `verified`, `conditional`, `unknown`; when impacts differ, its entries must conservatively reflect the least certain impact. A verified lock and unknown rewrite must not collapse to one verified score. `context_hints_used` is an array of objects `{ "table": "public.users", "size": "large", "source": "user_config" }`; empty means none, not evidence of a small table. Numeric `confidence` retains its v1 meaning and is not recalibrated silently. For DROP INDEX relation may be null even when mode is known; multiple relations or subcommands require multiple impacts or explicit unknown, not a misleading single relation. `runtime_contention` is always `unknown`, with no prediction or live observation.

Test a vendored v0.1.0 `ScanReport.model_validate_json` against default v0.2 JSON including parse errors and action fallback. Assert v2 is rejected by v1 as expected, accepted by v2, and that opt-in does not affect decisions, exit codes, findings ordering, or v1 byte output for unchanged findings. Gate richer fields from GitHub metadata until separately designed and explicitly opted in.

## 5. Ephemeral PG16 integration specification

**Not executed in this audit.** Harness is test-only and separate from production imports. Resolve an official PostgreSQL 16 image to a specific immutable digest during a connected preparation step; record the exact digest, minor version and architecture in the CI config. Do not invent a digest. Pre-pull/cache that exact digest on the CI runner before entering the isolated job. The isolated job verifies `docker image inspect`, runs with `--pull=never --network=none`, no published ports, and fails clearly if absent; it never pulls. The image may start PostgreSQL with `listen_addresses=''` and a private Unix socket; `docker exec -i ... psql -X -v ON_ERROR_STOP=1` sessions connect to **that disposable local container only**. This is a test fixture exception, never a SafeGate runtime connection. Set deterministic credentials only inside the disposable fixture, clean database and container in `finally`, and label uniquely for concurrent jobs. Pin dependencies/cache before isolation too. CI must fail rather than silently skip this required suite; local absence may produce a documented explicit skip.

Use multiple long-lived psql processes over `docker exec`, each exposing `pg_backend_pid()`, with SQL output sentinels and an observer session. Poll `pg_locks` for exact relation OID, backend PID, `mode` and `granted`; bounded polling fails the test with diagnostics rather than inferring blocking from elapsed time. Release the holding transaction and assert the waiting operation completes. Test-harness watchdogs prevent hangs; permission and timeout behavior are not product scenarios. Force `enable_indexscan=off` only where useful; for DROP test use a plain sequential read so the lock assertion does not depend on index use. Query [pg_locks](https://www.postgresql.org/docs/16/view-pg-locks.html) and [pg_blocking_pids](https://www.postgresql.org/docs/16/functions-info.html) as test-only observers.

| Case | Setup and assertions |
| --- | --- |
| A: CREATE INDEX | Session A `BEGIN; CREATE INDEX ...;` and signal after completion while transaction remains open. Observer confirms A's granted `ShareLock` on heap. Session B asynchronously `INSERT`; observer confirms B's ungranted `RowExclusiveLock` and A in `pg_blocking_pids`; independent plain SELECT succeeds. A COMMIT then B finishes. |
| B: DROP INDEX | Precreate index. A `BEGIN; DROP INDEX ...;` and hold transaction; observer confirms granted `AccessExclusiveLock` on heap. B plain SELECT waits with ungranted `AccessShareLock`, and A is its blocker. COMMIT A, then B completes. Assert SG-002 reports potential read and write conflict. |
| C: volatile default | Populate a normal heap; capture `pg_relation_filenode('public.t')`, OID, tablespace, values. Execute `ALTER TABLE ... ADD COLUMN ts timestamptz DEFAULT pg_catalog.clock_timestamp()`; compare filenode after commit and verify values. Expected new filenode indicates rewrite in this isolated case. |
| D: nonvolatile default | On a fresh populated heap repeat with `DEFAULT 42` and separately `DEFAULT pg_catalog.now()` on timestamptz. Assert unchanged heap filenode and correct old-row values. Verify ACCESS EXCLUSIVE separately; metadata-only does not mean no lock. |
| E: conversion | Fresh nonempty heaps: varchar(10)→varchar(20), varchar(10)→unbounded, varchar(20)→varchar(10) with fitting input, unbounded→varchar(10), integer→bigint, text↔unbounded varchar, identity vs transforming USING. Assert expected heap filenode equality/inequality and data, plus an overlength narrowing failure without misclassifying it as a successful rewrite. For partitioned tables inspect each leaf with `pg_partition_tree` and `pg_relation_filenode`, not the storage-less parent; use a supported alteration and verify independent leaf results. |
| F: offline static | With no DB container or socket available, run the real CLI against SG-001/002/003/004/006/009 fixtures in `--network=none`; compare findings, report and exits to ordinary offline execution. Guard against socket/database-driver use in the scanner process. The scanner must never discover or connect to the test server. |

For C–E use `pg_relation_filenode` (not raw `relfilenode` alone) and `pg_relation_filepath`, plus table OID and tablespace before/after. Keep tablespace fixed for the primary test, and test a separate tablespace move as a negative control: filenode/path can change for reasons other than the operation under test. Never infer rewrite from path change alone; compare heap and index separately and exclude partitioned parents, views, foreign tables and other relations without physical storage. A stable filenode does not prove no scan or no row updates. See [PG16 administration functions](https://www.postgresql.org/docs/16/functions-admin.html), [file layout](https://www.postgresql.org/docs/16/storage-file-layout.html), [partitioning](https://www.postgresql.org/docs/16/ddl-partitioning.html), and [ALTER TABLE tablespace](https://www.postgresql.org/docs/16/sql-altertable.html).
